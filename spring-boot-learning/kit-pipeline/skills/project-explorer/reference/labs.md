# Labs

A lab makes one ladder level happen on the learner's machine: the threshold crosses, the mechanism reacts, the
numbers move. Labs are optional and always gated: ask before building any of them.

## The labs gate (ask with AskUserQuestion, after the concepts are known)

Ask, in one go:

1. **Do you want labs?** Options: labs for every concept · labs for chosen concepts only · no labs (pages only).
2. **Failure switches**: may I add small dev-only switches to make a dependency slow or fail (off by default, config
   only, tested)? Or only use what exists (stop a container, kill a process)?
3. **Scale target**: what should the ladders reach (today's traffic, 10×, 100×)? This decides how many levels.
4. **Where may load run?** This laptop only (default) · a machine you own · plan-only (no load at all).

Record the answers in PROGRESS.md. Never send load to shared, staging or production systems; on a shared host,
labs that need real traffic stay plan-only.

## What a lab is made of

| Part | Rule |
|---|---|
| A run config | One launch config (or script) per lab variant, named `Lab · <what>`: e.g. limits off, two instances, a partner down, one shard. Env/args only; no code edits to switch labs |
| A load or fault driver | `tools/lab-kit.mjs` (burst / flood / probe / poll), extended with project commands (lag, reconcile, a DB count). Localhost only by default |
| A failure switch, if approved | See below |
| Steps | 3–6 numbered steps: start X, run Y, **Check:** what you should see (number, status code, log line, dashboard). Then reset |
| A measurement | Run it yourself first. Record date, machine, command, config and raw output in MEASURED.md; put the result on the page tagged `measured` |

## Failure switches (dev-only fault injection)

- A decorator/wrapper around the dependency client, enabled by config (`<app>.drill.<dependency>.failure-rate`,
  `.delay`), **off by default**, and absent from production profiles.
- When on, log a WARN at startup: `DRILL ON: <dependency> fails 30% of calls, each delayed 2s`.
- When off, return the real client itself (no wrapper in the call path).
- Unit-test it: off = not wrapped; rate 1.0 fails every call without calling through; a given rate fails that share
  (inject the random source); delay delays.
- Prefer existing seams: stopping a container, `docker pause`, toxiproxy, a stub's own error mode, a feature flag.

## Running labs safely

- Before load: check free disk (Docker VM too), and that nothing else is consuming the queues/DB you'll fill.
- Use unique ids per run (`lab-<run>-<n>`) so you can find, count and clean up your own data.
- Don't touch shared state to tidy up (consumer-group offsets, shared databases, other projects' containers): ask.
- Stop what you started. Leave the machine as you found it, and say what you left behind (data rows, volumes).
- Pausing in a debugger during a lab changes the result (timeouts, rebalances); measure without breakpoints.
